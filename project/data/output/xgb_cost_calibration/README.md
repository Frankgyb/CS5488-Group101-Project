# xgb_cost_calibration — outputs of the XGBoost cost calibration

Measurement output only. **No model artifact, no prediction, no train/test metric that belongs to
the deliverable.** Produced by `project/code/ml/experiments/xgb_cost_calibration/`; the narrative
that quotes these numbers is `handoff/ML/future_work_xgboost.md` §3.

```
metrics/
├── scan_and_sample.json      data-side cost: full 471.7 M-row feature pass + 5 % sample write
├── xgb_train_probe.json      driver-side XGBoost throughput, depth6/8, nthread axis
├── spark_ml_probe.json       JVM-side GBT / RF unit cost (2 M rows, local[8])
├── python_worker_probe.json  why workers failed (interpreter resolution), what fixed them
├── spark_xgb_probe.json      distributed SparkXGBRegressor unit cost (workers 4 vs 8)
└── calibration_summary.json  digest of all of the above + step statuses
```

## Caveats when quoting

* Each JSON is a **single run**. Two batches of the same probe differed by up to 1.7×
  (depth6: 0.706 vs 1.179 s/round), so these are cost estimates, not results. Anything that goes
  into the report needs 3 repeats and a median (`handoff/ML/timing_provenance.md` §7).
* `python_worker_probe.json` records a **correction**: the original diagnosis (`pyspark/daemon.py:29`
  importing POSIX signals) was wrong. The worker failure was `PYSPARK_PYTHON` not being set, so Spark
  launched `python3`, which does not exist here. With the variable set, RDD jobs and
  `SparkXGBRegressor` both succeed — see the `verdict` object in that file.
* Regenerate everything from the repository root with
  `D:/Anaconda/python.exe project/code/ml/experiments/xgb_cost_calibration/run_calibration.py`
  (~8–10 min; the 5 % sample is rewritten as a side effect).
